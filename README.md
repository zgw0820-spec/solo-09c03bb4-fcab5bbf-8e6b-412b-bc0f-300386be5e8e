# 机房重启指令下发（FastAPI + SQLite + Docker Compose）

两服务：操作网页（`web`，端口 8000）与本地边缘网关模拟器（`gateway`，端口 8001）。
两个服务各用一份 SQLite 文件，均挂在命名卷上，容器重启后数据不丢。

## 启动

```bash
docker compose up --build
```

- 操作网页：<http://localhost:8000>
- 网关真实执行记录：<http://localhost:8001/api/executions>

## 网页功能

- 提交：设备号、指令号、截止时间（分钟，相对当前时间）、可勾选“模拟丢回执”。
- 列表 / 详情：状态、回执状态、说明、下发尝试次数、回执是否丢失，每 2 秒自动刷新。
- “触发丢回执”按钮：
  - 指令还没发出时，下次下发让网关照常执行、但不返回回执；
  - 指令已在飞（网关仍在模拟设备延时中）时，通知网关丢弃这次响应，执行记录保留。

## 换盘对账（网关磁盘更换后的历史核对）

值班员更换网关磁盘后，在首页“网关换盘后对账”输入设备号发起对账。系统只对网页**已确认
执行结论**（`executed` / `failed`）的指令，按指令号逐号向网关核对可信执行记录；
`pending` / `inflight` 指令不在范围内，继续走各自的下发与核实规则。

每条指令给出五种结论之一：

| 结论 | 含义 |
| --- | --- |
| 一致（快照时点） | 网关记录的设备号、执行结论与网页一致；仅代表本次快照时点，不追溯之后的变化 |
| 网关记录缺失 | 网关已无该指令记录（HTTP 404） |
| 设备号冲突 | 网关同指令号记录属于另一个设备号 |
| 执行结论冲突 | 成功/失败结论不一致，或网关记录仍是 `running`/`unknown` 等无可信结论状态 |
| 未核实（网关不可达） | 网关连不上、超时或返回不可用响应；**既不算一致，也不算丢失** |

对账规则与后果：

- **快照隔离**：发起时固定本批次核对的指令集合。扫描期间该设备新确认的结果不会被塞进
  当前批次，旧的“无差异”结论也不会被改写成“当前一致”；批次页会显示快照之后新增的已确认
  指令数量，需要另行发起对账。
- **差异即持久标记**：出现“缺失/设备号冲突/结论冲突”任一差异，设备立即写入 `device_flags`
  持久标记为待排查，调度器从此不再认领该设备的**新**指令；已在下发（inflight）或待核实的
  指令维持原有核实与同设备顺序规则，其他设备照常处理。
- **未核实不标记**：网关不可达只产生“未核实”，批次状态为 `done_unverified` 且不落待排查
  标记；网关恢复后重新发起对账即可。
- **重启可查**：对账批次、逐条结论、待排查标记都存在网页侧 SQLite（命名卷），两服务重启后
  仍可查看，标记在重启后继续生效。标记只能由人工通过
  `POST /api/reconcile/flags/{device_id}/clear` 解除，系统不会自动清除。

对账相关接口：`POST /reconcile`（表单）、`POST /api/reconcile`（JSON）、
`GET /reconcile/runs/{id}`（明细页）、`GET /api/reconcile/runs/{id}`、
`GET /api/reconcile/flags`、`POST /api/reconcile/flags/{device_id}/clear`。

## 语义与实现要点

| 要求 | 实现 |
| --- | --- |
| 同号重复提交返回原结果 | `command_id` 唯一；重复提交读原记录、不改状态、不重新排队 |
| 同设备按提交顺序执行 | 每轮只认领该设备最早的一条 `pending`，按自增 `id` 排序 |
| 前条回执未明时后条等待 | 只要设备有 `inflight` 指令，该设备所有后续指令都不下发，与它是否过期无关 |
| 其他设备照常下发 | 阻塞按 `device_id` 分组，不同设备互不影响 |
| 回执丢失按指令号核实、不当失败重跑 | 收到“丢回执”响应后仍保持 `inflight`，用 `GET /api/commands/{id}` 核实；只有核实出明确结果才结案 |
| 未发出的指令过期 → 未执行 | `pending` 且超过 `deadline` → `unexecuted`，之后不再下发 |
| 已发出、结果未明的过期后仍待核实 | `inflight` 不参与过期清理；继续核实，继续阻塞本设备队列 |
| 重启后继续处理未结指令 | 启动时把“已认领但未写出网络”的指令放回队列；`inflight` 指令继续按指令号核实 |
| 已执行的指令不得再执行 | `executed` 为终态；网关侧 `executions` 计数与唯一主键双重保证同一 `command_id` 最多执行一次 |

网关侧的额外保证：

- 执行记录与回执在同一事务里提交，所以“执行了但回执丢了”永远可以通过指令号查到；
- 收到重复投递只回放已存的回执，不会第二次执行；
- 网关在执行途中被杀，重启后该 `command_id` 冻结为 `unknown`（可能已执行、无法证明），
  之后任何重复投递都不会执行它，网页端也把它保持为待核实而不是失败。

## 状态

`pending`（等待下发）→ `inflight`（已发出，等待回执/核实）
→ `executed` / `failed` / `unexecuted` / `rejected`

`inflight` 不是终态，也不是失败：它可能是执行成功但回执丢失，必须按指令号核实。

## 自测

```bash
python -m pytest -q          # 38 项：状态机单测 + 双服务集成测试（含丢回执、断开、重启、换盘对账）
```

E2E 脚本覆盖：丢回执核实、同设备串行、跨设备并行、重复提交、在飞丢回执、
网关宕机时保持待发、双服务重启续作、网关执行中被 SIGKILL 后指令号冻结，以及换盘对账
（一致/缺失差异并落待排查标记、标记设备新指令不认领且他设备照常、网关不可达记未核实、
双服务重启后标记与差异仍在、恢复后重新对账）。
